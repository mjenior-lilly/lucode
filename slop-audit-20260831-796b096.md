## 4. Findings register

### Bug

#### 1. Thread-pool context managers defeat all three MCP discovery deadlines

   Category:      bug  
   Severity:      high  
   Confidence:    confirmed  
   Verification:  coordinator-verified  
   Location(s):   `src/ucode/databricks.py:1660-1675`; `src/ucode/databricks.py:1736-1799`; `src/ucode/databricks.py:1815-1914`; `src/ucode/databricks.py:1917-2019`; `src/ucode/mcp.py:936-974`; `src/ucode/mcp.py:1236-1246`  
   Signal:        n/a (Class A behavior claim)  
   Evidence:      Each discovery function calls `_drain_with_deadline`, then `pool.shutdown(wait=False, cancel_futures=True)` inside `with ThreadPoolExecutor(...)`. Leaving that `with` calls `Executor.__exit__`, whose installed standard-library implementation is `self.shutdown(wait=True)`. Running futures therefore still block function return after the 15, 20, or 30 second deadline. `_paginated_json_items` permits 50 pages at a 10-second request timeout, so one running worker can outlive the stated budget by minutes. `mcp-services` is selected by default and `_discover_selected_mcp_sources` always invokes the workspace-wide walk for it.  
   Why it hurts:  `ucode configure mcp` can keep spinning long after its documented wall-clock budget on a slow workspace. The explicit non-waiting shutdown gives maintainers false confidence because the context manager immediately reverses it.  
   Blast radius:  Vector Search discovery, UC Functions discovery, workspace-wide MCP-service discovery, the default MCP setup wizard, and deadline-focused tests that need to be added.  
   Effort:        medium  
   Action:        refine  

#### 2. Pi's fallback selector rejects available OpenAI-only workspaces

   Category:      bug  
   Severity:      high  
   Confidence:    confirmed  
   Verification:  coordinator-verified  
   Location(s):   `src/ucode/agents/pi.py:251-292`; `src/ucode/agents/__init__.py:159-166`; `src/ucode/agents/__init__.py:181-190`; `tests/test_agent_pi.py:210-234`; `tests/test_agents_init.py:171-194`  
   Signal:        n/a (Class A behavior claim)  
   Evidence:      `check_gateway_endpoint` declares Pi available when `codex_models` is non-empty. `default_model` then considers only model names containing `sol`, `terra`, or `luna`; an ordinary discovered ID such as `gpt-5` leaves `selected` as `None`. `resolve_launch_model` converts that to `RuntimeError("No models available for pi...")`. The production trace is `configure_single_tool` or launch setup -> `resolve_launch_model` -> `default_model`. Both focused test modules state that a `codex_models=["gpt-5"]` or `["c1"]` state must fall back to that first model. The same implementation also walks every Anthropic key and every matching Google family without returning, so later entries overwrite earlier priorities.  
   Why it hurts:  A workspace that exposes Pi-compatible OpenAI models but no Claude models passes the availability gate and then fails configuration. Selection also depends on list and dict iteration rather than the documented family order.  
   Blast radius:  Pi first-time configuration, bare Pi launch, derived Pi state, token-refresh model selection, and default-model tests in two modules.  
   Effort:        small  
   Action:        refine  

#### 4. `mcp-proxy --use-pat` accepts the flag but never activates PAT authentication

   Category:      bug  
   Severity:      medium  
   Confidence:    confirmed  
   Verification:  coordinator-verified  
   Location(s):   `src/ucode/cli.py:818-852`; `src/ucode/mcp_proxy.py:61-83`; `src/ucode/mcp_proxy.py:101-119`; `src/ucode/mcp_proxy.py:136-158`; `tests/test_mcp_proxy.py:129-147`  
   Signal:        n/a (Class A behavior claim)  
   Evidence:      The hidden CLI promises `--use-pat` will "Use the profile's static PAT instead of OAuth" and passes the boolean to `serve`. `_DatabricksTokenAuth` stores it as `_use_pat`, but `auth_flow` ignores the field and calls `get_databricks_token` directly. `_preflight_token` also has no `use_pat` parameter. Unlike `auth_token_cmd`, this path never calls `ensure_pat_bearer`. The tests only prove that `True` reaches `_run`; they do not prove that token resolution changes.  
   Why it hurts:  A proxy process started without an inherited `DATABRICKS_BEARER` takes the OAuth path even when its persisted command includes `--use-pat`, producing an authentication failure for a PAT-only profile.  
   Blast radius:  OpenCode MCP registrations created with `--use-pat`, the hidden `mcp-proxy` command, request-time token refresh, and proxy authentication tests.  
   Effort:        small  
   Action:        rewire
